# Ответы на вопросы защиты — Практическая работа № 8

## 1. Чем бинарный файл отличается от текстового на уровне Python?

На уровне Python разница не в «содержимом диска», а в **режиме открытия и типе возвращаемых данных**.

| Режим | Тип данных | Что делает |
|-------|------------|------------|
| `open(p, "r", encoding="utf-8")` | `str` | Декодирует байты в символы по указанной кодировке; включает «универсальные переводы строк» (`\r\n` → `\n` при чтении, `\n` → системный разделитель при записи). |
| `open(p, "rb")` | `bytes` | Отдаёт байты как есть: без декодирования, без замены переводов строк, без кодировочных ошибок. |

Следствия:

- Текстовый режим можно использовать только когда известна кодировка; иначе получим `UnicodeDecodeError` или нечитаемые символы.
- Бинарный режим применим к чему угодно: картинка, ZIP, `.bin`, а также к тексту, если нам нужны именно байты.
- В этой работе `sha256_file()` намеренно открывает файл через `path.open("rb")` и считает `hashlib.sha256()` от `bytes`. Если бы мы считали хеш от `str`, результат зависел бы от кодировки и перевода строк и не совпадал бы с хешом исходных байтов.

Пример из кода:

```python
with path.open("rb") as file:      # bytes, без преобразований
    chunk = file.read(4096)
    hasher.update(chunk)
```

Кратко: **текстовый режим = `str` + кодировка + нормализация строк; бинарный = `bytes` «как есть»**.

## 2. Какие проблемы решает инструкция `with`?

`with` использует протокол контекстного менеджера (`__enter__` / `__exit__`) и гарантирует **выполнение кода очистки при любом исходе блока**:

1. **Закрытие файла даже при исключении.** Если внутри блока упал `ValueError`, `with` всё равно вызовет `file.close()`. Без `with` файл останется открытым до сборки мусора, а в PyPy или при наличии ссылок из traceback — ещё дольше.
2. **Сброс буфера записи.** При закрытии буферизованные данные гарантированно попадут на диск. Если забыть `close()`, конец файла может не записаться.
3. **Защита от утечки дескрипторов в циклах.** При обработке сотен файлов ручной `open()` без `close()` быстро приведёт к `OSError: Too many open files`.
4. **Единообразие для других ресурсов.** `with` работает не только с файлами, но и с `ZipFile`, блокировками, соединениями — везде, где есть `__exit__`.

В работе `with` используется и при чтении (`sha256_file`), и при записи (`destination.open("xb")`), и при работе с архивом (`with ZipFile(...) as archive`). Это значит, что ZIP корректно закроется и после ошибки проверки.

Эквивалент без `with` — громоздкий `try/finally`:

```python
file = path.open("rb")
try:
    ...
finally:
    file.close()
```

## 3. Почему режим `w` опасен для существующего файла?

Режим `w` (write) **сразу при открытии обрезает файл до нуля**, даже если мы ещё ничего не записали:

```python
with open("important.txt", "w") as f:   # файл уже пустой!
    f.write("новые данные")
```

Опасность в том, что:

- старые данные утрачиваются **необратимо** (корзины и журнала нет);
- если между открытием и записью произойдёт ошибка, файл останется пустым;
- легко случайно перезаписать чужой файл из-за неверного имени.

Более безопасные режимы:

| Режим | Поведение |
|-------|-----------|
| `x` / `xb` | Создаёт файл **только если его нет**, иначе `FileExistsError`. Атомарная проверка на уровне ОС (`O_EXCL`), нет «гонки» между проверкой и созданием. |
| `a` / `ab` | Добавляет в конец, не стирая старое содержимое. |
| `w` | Перезаписывает/создаёт — использовать осознанно. |

В `receive_package()` мы используем именно `xb`:

```python
with destination.open("xb") as file:
    file.write(content)
```

Если файл уже есть, приём упадёт с `FileExistsError`, но **существующие данные не пострадают**. Это и есть ответ на вопрос «какой режим защищает от перезаписи».

## 4. Чем отличается шаблон `*.txt` от реальной проверки формата?

`fnmatch.fnmatch(file.name, "*.txt")` смотрит **только на имя файла** (строку), а не на его содержимое. Поэтому:

- файл `virus.bin` можно переименовать в `notes.txt` — шаблон его пропустит;
- настоящий текстовый файл с именем `notes.dat` шаблон отсечёт;
- на Windows `fnmatch` сравнивает без учёта регистра, поэтому `NOTES.TXT` тоже подойдёт (для строгой проверки есть `fnmatch.fnmatchcase`).

Реальная проверка формата смотрит на **байты/структуру**:

- «магические» сигнатуры (например, `PK\x03\x04` у ZIP, `\x89PNG` у PNG);
- успешное декодирование ожидаемой кодировкой и отсутствие нулевых байтов для текста;
- разбор по формату (JSON → `json.loads`, CSV → `csv.reader`, ZIP → `ZipFile`).

В нашей работе `scan_files()` решает только задачу **поиска по имени и размеру** — это фильтр, а не проверка формата. А вот приём пакета уже проверяет содержимое: `size_bytes` и `sha256` подтверждают, что полученные байты совпадают с теми, что были у отправителя. Но и это не «проверка, что файл текстовый» — это проверка целостности.

Итог: **шаблон — это удобный быстрый фильтр по имени; формат определяется содержимым.**

## 5. Почему нельзя сразу сохранять содержимое полученного ZIP?

Потому что ZIP — это «контейнер с чужими данными», и до записи на диск нужно убедиться в его безопасности и целостности. Иначе возможны:

1. **Path traversal.** В манифесте может быть `filename = "../notes.txt"`, `"/etc/passwd"` или `"..\\notes.txt"`. Тогда файл запишется вне `inbox` или поверх чужого файла. Мы проверяем:

   ```python
   Path(name).name != name or "/" in name or "\\" in name or name in ("", ".", "..")
   ```

2. **Не тот получатель.** Пакет может быть адресован другой команде. Проверяем `manifest["recipient"]`.

3. **Подмена данных.** Байты в архиве могут отличаться от заявленных. Сверяем длину и `hashlib.sha256(content).hexdigest()` со значением из манифеста.

4. **Перезапись существующего файла.** Даже корректный пакет не должен молча затирать уже принятый файл — поэтому запись идёт через `xb`.

5. **Корректность самого манифеста.** Нет `manifest.json`, некорректный JSON, отсутствует `files/<имя>` — всё это должно привести к `ValueError`, а не к сохранению мусора.

Принцип: **сначала все проверки в памяти, и только потом единственная запись на диск**. Тогда при любой ошибке `inbox` остаётся чистым — это и демонстрирует тест `test_04_corrupted_file_is_rejected` и `tamper_demo.py`.

## 6. Подтверждает ли хеш личность отправителя?

**Нет.** SHA-256 подтверждает только **целостность данных**: «эти байты не изменились с момента вычисления хеша».

Почему этого мало для подлинности:

- функция хеширования открытая и детерминированная: злоумышленник может изменить файл и пересчитать `sha256`, положив новое значение в манифест;
- поле `"sender": "team_A"` — простое слово из того же манифеста, его тоже можно подделать;
- хеш не содержит секрета и не привязан к ключу или удостоверению.

В лабораторной работе хеш защищает от **случайной или намеренной порчи при передаче** (испорченная копия от `tamper_demo.py` отклоняется), но не от подмены целиком.

Для подтверждения личности нужны:

- **электронная подпись** (отправитель подписывает хеш своим закрытым ключом, получатель проверяет открытым);
- либо **HMAC** с общим секретом;
- либо аутентификация канала (TLS, сертификаты).

Кратко: **хеш отвечает «не изменилось ли?», подпись отвечает «кто отправил?»**.

## 7. Как работает последовательный обход (доп. к «Что сдавать»)?

`Path.rglob("*")` рекурсивно обходит дерево каталогов и **по одному возвращает** найденные объекты (генератор), не загружая всё дерево в память сразу:

```python
for file in folder.rglob("*"):
    if not file.is_file():      # каталог пропускаем
        continue
    info = file.stat()          # только метаданные, чтение содержимого не нужно
    if not fnmatch.fnmatch(file.name, pattern):
        continue
    if info.st_size < min_size:
        continue
    result.append({...})        # компактная запись о файле
result.sort(key=lambda item: (item["name"], item["relative_path"]))
```

Итог — список словарей (имя, относительный путь, размер, время изменения), отсортированный по имени и пути. Память расходуется только на этот список, а не на содержимое файлов; время работы пропорционально числу файлов. Такой обход называют последовательным: каждый элемент обрабатывается сразу при получении, без построения полного дерева заранее.

## Короткая шпаргалка для устного ответа

- **От перезаписи защищает `xb`** — `FileExistsError`, если файл уже есть; `w` обрезает файл сразу при открытии.
- **Контрольная сумма** — «отпечаток» байтов: совпадает → данные не изменились; не совпадает → пакет подменён или испорчен. Личность не подтверждает.
- **Последовательный обход** — `rglob` выдаёт файлы один за другим, у каждого сразу берём `stat()`, фильтруем и сортируем итоговый список.
